# jtzero-kimera

Экспериментальный репозиторий для проверки Kimera-VIO на Raspberry Pi 5 в составе JT-Zero.

Цель первого этапа — получить нативную сборку Kimera-VIO на текущем RPi5 без Docker и ROS, запустить её на эталонном датасете EuRoC, измерить производительность, а затем перейти к живому потоку OV9281 + IMU.

## Фактическая тестовая платформа

На 2026-08-30 зафиксирована следующая базовая система:
- Raspberry Pi 5 Model B Rev 1.0;
- Debian GNU/Linux 13 (trixie), 13.5, Raspberry Pi kernel;
- ARM64 / aarch64;
- kernel 6.18.34+rpt-rpi-2712;
- CPU: 4× Cortex-A76, до 2.4 GHz;
- RAM: 4.0 GiB;
- swap: 2.0 GiB;
- корневой раздел: 15 GiB, свободно 6.6 GiB на момент проверки;
- GCC/G++ 14.2.0;
- Git 2.47.3;
- CMake на момент первичной проверки не установлен;
- температура CPU при проверке: 52.1°C;
- throttling: 0x0.

Эта конфигурация является исходной точкой для native-сборки. Все несовместимости Kimera-VIO и её зависимостей с Debian 13 / GCC 14 фиксируются в этом репозитории по мере прохождения этапов.

## План работ

### Этап 1. Проверить текущее окружение Raspberry Pi 5

Зафиксировать:
- модель Raspberry Pi;
- архитектуру ОС;
- версию Debian / Raspberry Pi OS;
- версию ядра;
- объём RAM;
- свободное место;
- наличие активного охлаждения;
- версии GCC, CMake и Git.

Пример команд:

```bash
uname -a
cat /etc/os-release
uname -m
free -h
df -h
gcc --version
cmake --version
git --version
```

Ожидаемая платформа — 64-bit ARM64.

### Этап 2. Подготовить системные зависимости

Установить базовые инструменты сборки:

```bash
sudo apt update
sudo apt install -y \
  build-essential \
  cmake \
  git \
  pkg-config \
  libeigen3-dev \
  libopencv-dev \
  libgoogle-glog-dev \
  libgflags-dev \
  libboost-all-dev \
  libsuitesparse-dev \
  libtbb-dev
```

Точный список зависимостей будет уточняться после первой попытки конфигурации Kimera-VIO под текущий Debian.

### Этап 3. Собрать зависимости Kimera

Kimera-VIO зависит от нескольких библиотек, в том числе:
- GTSAM;
- OpenGV;
- DBoW2;
- Kimera-RPGO;
- OpenCV;
- Eigen;
- glog / gflags.

Для Raspberry Pi 5 предпочтительна нативная ARM64-сборка всех компонентов с контролем версий.

Каждую крупную зависимость будем собирать отдельно, чтобы при ошибке было понятно, какой именно компонент несовместим с текущей системой.

### Этап 4. Собрать Kimera-VIO без ROS

На первом этапе ROS не используем.

Причины:
- меньше нагрузка на CPU и RAM;
- проще диагностировать ошибки;
- меньше зависимостей;
- проще затем подключить собственный захват OV9281 и MAVLink IMU;
- удобнее оценить чистую производительность Kimera-VIO на RPi5.

После установки зависимостей:
1. клонировать Kimera-VIO;
2. создать отдельный build-каталог;
3. выполнить CMake-конфигурацию;
4. собрать с разумным количеством потоков;
5. сохранить полный build log.

На Raspberry Pi не следует сразу использовать максимальное число потоков, если сборка приводит к нехватке RAM.

### Этап 5. Первый запуск на EuRoC

До подключения реального железа проверить Kimera-VIO на стандартном датасете EuRoC.

Начальный режим:
- mono + IMU;
- один из простых наборов, например V1_01_easy;
- штатная конфигурация Kimera для EuRoC Mono.

Нужно проверить:
- запускается ли pipeline без ошибок;
- обрабатываются ли все кадры;
- средний FPS;
- загрузку CPU;
- использование RAM;
- наличие пропусков кадров;
- стабильность оценки траектории.

Главная цель этого этапа — понять, способен ли текущий RPi5 выполнять Kimera-VIO с приемлемой скоростью до интеграции наших датчиков.

### Этап 6. Профилирование Raspberry Pi 5

Во время теста EuRoC измерить:
- загрузку каждого ядра;
- температуру CPU;
- частоту CPU;
- RAM;
- swap;
- реальную скорость обработки кадров.

Полезные команды:

```bash
htop
vcgencmd measure_temp
vcgencmd measure_clock arm
```

Если Kimera не держит real-time, последовательно уменьшать нагрузку:
- разрешение изображения;
- число features;
- частоту камеры;
- сложность frontend;
- дополнительные визуализаторы и отладочный вывод.

### Этап 7. Подключить OV9281

После успешного EuRoC-теста перейти к реальной камере.

Первый вариант допускает текущую USB OV9281.

Для конечной версии предпочтителен CSI OV9281, поскольку для VIO особенно важны:
- стабильная задержка;
- точный timestamp кадра;
- минимальный jitter между камерой и IMU.

Планируемые режимы для первого теста:
- grayscale;
- 640x480;
- 30 FPS;
- короткая фиксированная экспозиция;
- отключённые автоматические изменения параметров изображения, где это возможно.

### Этап 8. Получить RAW IMU с Matek H743

Для полноценного VIO не использовать только MAVLink ATTITUDE.

Нужны сырые измерения:
- angular velocity X/Y/Z;
- linear acceleration X/Y/Z;
- timestamp.

Целевая частота:
- минимум около 200 Hz;
- предпочтительно 200–400 Hz при устойчивой передаче.

Поток данных:

```text
Matek H743
   |
   | RAW IMU 200-400 Hz
   v
Raspberry Pi 5
   ^
   |
OV9281 30-60 FPS
```

### Этап 9. Временная синхронизация камеры и IMU

Это один из ключевых этапов.

Kimera должна получать изображение и IMU на общей временной шкале.

Нужно измерить и затем минимизировать:
- постоянный camera-to-IMU offset;
- jitter;
- задержку USB / CSI;
- задержку MAVLink / serial.

Для CSI-камеры в дальнейшем желательно использовать timestamp из camera metadata, а не время, когда приложение уже получило кадр.

### Этап 10. Калибровка камеры

Для OV9281 определить:
- fx;
- fy;
- cx;
- cy;
- коэффициенты distortion;
- фактическое разрешение.

Калибровка должна соответствовать той же оптике, фокусу и разрешению, с которыми будет работать VIO.

### Этап 11. Калибровка Camera ↔ IMU

Определить точное пространственное преобразование между:
- системой координат камеры;
- системой координат IMU / flight controller.

Нужны:
- rotation;
- translation;
- проверка знаков и направления осей.

Нельзя ограничиваться приближённым описанием вроде «камера смотрит вниз».

### Этап 12. Live Mono + IMU

После калибровки:
1. подать live grayscale OV9281;
2. подать RAW IMU;
3. привести timestamps к одной шкале;
4. запустить Kimera-VIO;
5. вывести pose и velocity;
6. логировать входные и выходные данные.

Первый тест проводить на столе:
- 5 секунд неподвижно;
- медленное перемещение по известной дистанции;
- возврат;
- отдельный yaw-тест;
- затем комбинированные движения.

### Этап 13. Сравнить с jtzero-optical-flow-mvp

Kimera не должна сразу заменять существующий optical-flow pipeline.

Нужно параллельно сравнить:
- drift в покое;
- ошибку на 500 мм;
- поведение при yaw;
- зависимость от скорости;
- восстановление после потери features;
- загрузку CPU;
- задержку;
- устойчивость к вибрации.

Итоговая задача — определить, какой вариант лучше подходит для стабилизации JT-Zero:
- лёгкий optical flow + rangefinder + IMU;
- полноценный VIO;
- либо гибрид обоих подходов.

## Ближайшая контрольная точка

Первая контрольная точка репозитория:

**Kimera-VIO нативно собрана на текущем Raspberry Pi 5 и успешно проходит EuRoC V1_01_easy в Mono+IMU режиме.**

До достижения этой точки не вносим изменения в основной optical-flow проект и не подключаем Kimera к ArduPilot EKF.
